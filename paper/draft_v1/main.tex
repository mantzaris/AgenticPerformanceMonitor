\title{Agentic Dashboards: Numerical Validity, Answer Completeness, and Adaptive Presentation}
\author{}
\keywords{Analytical Agents, Longitudinal Data, Evidence Provenance, Answer Completeness, Adaptive Dashboards.}
\abstract{A question such as "Has this student's activity changed, and how does it compare with their peers?" often requires a dashboard to bring several kinds of information together. We present an agentic dashboard system that organizes real educational activity and assessment records into views suited to different questions. A language model chooses predefined analyses and selects results. Deterministic tools calculate the quantities, validation links them to supporting records, and presentation templates arrange the selected information. The dashboards highlight personal change, compare peer groups and time periods, distinguish recorded zeros from unavailable observations, and present assessment histories. Users can switch among saved comparisons and inspect the evidence behind displayed values. We evaluate three selection interfaces using Qwen2.5-14B-Instruct on 24 development cases from two Open University course offerings. The interfaces produced \AVisible, \BVisible, and \CVisible\ complete visible answers, respectively, compared with \EnumVisible\ for a deterministic baseline. We also distinguish answers selected by the model from information added automatically by the dashboard software. The saved outputs reveal that correct, traceable values can still refer to the wrong period or leave part of a question unanswered. More explicit analytical labels did not improve the original completeness scores, and some equivalent answer forms still require human review. The contribution combines a working adaptive dashboard system, concrete interface examples, and a comparative evaluation showing how analysis selection, evidence checking, and presentation jointly shape the answers users receive.}

\section{\uppercase{Introduction}}
\label{sec:intro}
\noindent Dashboards can help people understand how their activity changes over time and how it compares with that of others. The most useful view, however, depends on the question. A student asking about recent progress needs a comparison with their own earlier activity. A student asking how they compare with others needs a suitable peer group. If recent observations are unavailable, the dashboard should explain the gap instead of suggesting a trend.
This paper develops an agentic dashboard tool around that idea. Using educational activity and assessment records, the tool presents views for personal change, peer comparisons, limited observations, and assessment history. Each view brings the relevant information into focus. For example, a reference selector lets the user explore saved comparisons, while an observation timeline distinguishes weeks with no recorded activity from periods when the student was not eligible to participate.

The system combines a language model with predefined analysis tools and presentation templates. The model chooses analyses and selects results to answer the question. The tools calculate the values, and the software checks their supporting records before assembling the dashboard. A separate presentation layer arranges the selected information into the different views. This division makes the displayed results traceable while allowing the content to vary across questions.
We examine three ways of providing analytical information to the model. These range from a compact interface to richer descriptions of data availability and comparison scope, followed by explicit labels identifying the measure, periods, and reference group. The same model and calculation tools are used throughout. A deterministic baseline selects the required analyses through predefined rules for the same question families.

The evaluation asks whether clearer analytical descriptions help the model produce more complete answers. It also distinguishes information selected by the model from context added automatically by the dashboard software. Inspecting the saved outputs shows where the system answers the question successfully and where it retrieves correct information but chooses an unsuitable comparison or leaves part of the question unanswered.
The contribution is a working dashboard system, a comparison of its selection interfaces, and concrete examples of its behavior. More explicit labels did not improve the original completeness scores. Some alternative answer forms still require human review. The interface examples illustrate practical adaptation, while the evaluation identifies limitations to address in further development.





\section{\uppercase{Related Work}}
\label{sec:related}
\noindent Adaptive dashboards connect research on language interfaces, visualization authoring, and analytical evaluation. NL4DV connects natural language queries to data attributes, analytical tasks, and Vega-Lite specifications \cite{nl4dv}. NL4DV-LLM extends this approach with conversational interaction and ambiguity handling \cite{sah2024}. These systems motivate translating a user's question into explicit analytical choices. For longitudinal data, those choices include the measure, time periods, and whether the comparison concerns personal history or peers.

Those choices must then become a useful display. LIDA combines data summarization, goal exploration, visualization code generation and evaluation, and infographic generation \cite{lida}. Data Formulator~2 supports iterative authoring through graphical and natural language inputs, generated data transformations, and branching histories \cite{dataformulator2}. Our system adopts a narrower division of work. The model selects predefined analyses and results, while calculation tools and presentation templates produce the dashboard. This supports different views while keeping calculations and presentation rules available for inspection.

Declarative visualization provides a design model for this separation. Vega-Lite expresses visual encodings and interactions through specifications that compile into graphical displays \cite{vegalite}. Draco represents visualization design knowledge through hard and soft constraints \cite{draco}. Our templates similarly control how selected information becomes a view. Personal timelines, peer comparisons, and observation summaries can therefore use different presentations while retaining consistent meanings for values, periods, and availability.
These design choices also shape the evaluation. InsightBench studies agents that formulate questions, perform analyses, and summarize insights using datasets containing planted patterns \cite{insightbench}. Here, the questions are supplied, and the observations come from real educational records. We examine whether the model selects enough information to answer each question. Holding the calculation and presentation machinery fixed helps identify failures in selection, including choosing an earlier period when the question concerns recent activity.

VisEval further distinguishes executable validity, satisfaction of chart and data requirements, and readability \cite{viseval}. Its acceptance of multiple valid charts is particularly relevant to assessing our dashboards. A requested value may appear in different supported answer forms, so checking one expected representation can miss a valid response. This motivates separate checks of numerical support and answer completeness. Some equivalent forms in our development comparison still require human adjudication.
W3C PROV-DM provides concepts for describing entities, activities, agents, and derivations \cite{prov}. This perspective motivates tracking the source results, model selections, automatically supplied context, and final presentation separately. Together, these research strands inform our development of a longitudinal dashboard system and a comparative study connecting what the model selects, what the software adds, and what the user can inspect.









\section{\uppercase{Data and Analytical Definitions}}
\label{sec:data}
\noindent To help operators interpret changes in activity, the dashboards need consistent definitions of time, participation, and available records. We use the Open University Learning Analytics Dataset (OULAD), which links course offerings, registrations, assessments, and virtual learning environment interactions \cite{oulad}. The creator deposited UCI archive is distributed under CC BY~4.0 \cite{ouladDataset}. Our audit counted 28,785 distinct people, 32,593 registrations in course offerings, 173,912 assessment records, and 10,655,280 interaction rows. People and registrations are counted separately because a person can register more than once. To avoid multiplying counts when combining sources, we checked duplicate keys and many-to-one joins and aggregated interaction and assessment records before constructing weekly features.

\subsection{Development Population and Time}
We selected two offerings from different modules, AAA\_2013J and BBB\_2013B, to develop dashboards with sufficient history for comparisons. Selection followed lexical order and required 100 development people with eight fully eligible weeks and two dated non-examination assessments by day~83. The offerings contained 254 and 1,269 development registrations, representing 1,523 distinct people. These criteria selected usable record structures without targeting unusually high or low activity.

A hash of person identifiers assigned approximately 70\% of people to development and reserved 8,583 people, keeping all registrations for each person together. A global structural audit preceded preparation. Reserved observations were not used for case selection, fitting, prompt development, or the present comparison, which remains a development study.

Each dashboard summarizes activity by person, offering, and week. Day~0 marks the offering's start, and week~$w$ covers days $7w$ through $7w+6$. Only calendar weeks ending by the analytical cutoff are included. Within a week, eligibility starts at registration and ends before the withdrawal day. Future withdrawal is masked, and unknown registration leaves eligibility unknown. These rules help distinguish gaps in participation from recorded inactivity. They reconstruct availability retrospectively and have not been validated as a real-time feed.

\subsection{Recorded Measures and Availability}
To account for differences in eligible time, we express recorded clicks as a daily rate. For person $i$ in week $w$, let $d_{iw}$ denote administratively eligible days and $c_{iw}$ the recorded clicks on those days. The rate is
\begin{equation}
x_{iw}=c_{iw}/d_{iw},\qquad d_{iw}>0.
\label{eq:rate}
\end{equation}
The dashboard shows this rate as unavailable when eligibility is unknown or there are no eligible days. An eligible week without recorded clicks receives zero. This distinction helps operators read gaps correctly, although logging completeness remains unknown. Absent clicks establish neither logging failure nor lack of effort, and click counts do not measure ability, study time, or learning.

Other weekly measures provide complementary views of the records. These include days with positive activity, distinct resources, non-banked submissions, and scheduled assessments without a recorded submission. Submissions count in their recorded week, within eligibility and the cutoff. The scheduled measure counts dated non-examination assessments due during an eligible part of the week without a non-banked submission by that week's end. It describes recorded opportunities, since unknown exemptions prevent interpreting every missing submission as an unmet obligation. Later submissions do not rewrite earlier status snapshots.

To keep historical views consistent with their cutoff, agent inputs exclude future activity, final results, and future withdrawal. Assessment scores are withheld because submission dates do not establish when grades became available. Banked assessments transferred from earlier offerings are excluded from prospective counts because approval timing is unknown. Grade unavailability therefore reflects missing timing information, rather than insufficient sample size. All conditions use these rules.

Repeated source rows remain a measurement limitation. The primary analysis sums them, while the audit identified 787,170 exact duplicate excess rows and 2,195,960 excess rows under a candidate 'person-offering-site-day' key. That key is not assumed to identify unique events. An earlier, limited sensitivity check removed exact duplicates, but it does not establish robustness across the present cases. The interpretation of repeated rows still requires review.

\subsection{Personal and Peer Comparisons}
The dashboard uses consistent summaries to connect personal progress with peer comparisons. Let $O_i(W)$ contain eligible weeks with recorded values for a feature in period $W$. The person's mean, unavailable when this set is empty, is
\begin{equation}
m_i(W)=\frac{1}{|O_i(W)|}\sum_{w\in O_i(W)}x_{iw}.
\label{eq:person}
\end{equation}
Weeks receive equal weight, including partial weeks after calculating their daily rates. This differs from dividing total clicks by total eligible days. Personal change $\Delta_i=m_i(W_r)-m_i(W_b)$ requires at least two observed weeks in both the recent and earlier periods.

For reference group $g$ and period $W_g$, let $P_g$ contain eligible peers with at least one nonmissing week. The peer mean and the person's difference from it are
\begin{align}
\mu_g(W_g)&=\frac{1}{|P_g|}\sum_{j\in P_g}m_j(W_g),\\
D_{i,g}&=m_i(W_r)-\mu_g(W_g).
\end{align}
Each person receives equal weight. Comparisons require 20 peers and two observed weeks for the person being assessed. Means may remain available below these thresholds. These prototype rules are not validated educational decision criteria.

Operators can examine three reference groups using these shared definitions. They include other development students in the same offering, students additionally sharing first-attempt or repeat-attempt status, and same-offering peers observed in the earlier period. The person being assessed and all other designated task participants are excluded from peer groups across their registrations. These alternatives make the choice of comparison visible. Earlier-period comparisons can differ in membership, observed history, and actual exposure, so they are not necessarily fairer or causally adjusted. Weekly peer trajectories always use eligible peers from the same week, even when an accompanying summary uses an earlier reference period.

To show uncertainty around peer means, we draw 500 seeded bootstrap samples of people with replacement, retain each person's period mean, and use the 2.5th and 97.5th percentiles \cite{efron}. Weekly bands repeat this procedure separately for each week and describe uncertainty at each point, rather than across the whole trajectory. No interval is shown with fewer than two peers. These intervals describe peer means only. They do not predict individual activity or quantify uncertainty in personal change, $D_{i,g}$, or differences between reference choices. Fixed seeds make the calculations reproducible without establishing generalization beyond the selected offerings. The dashboards use these descriptive calculations. A separate exploratory mixed-model analysis is not a validated detector and supplies no dashboard claims.

\section{\uppercase{From Questions to Dashboards}}
\label{sec:system}
\noindent Our approach connects flexible analysis selection with checked calculations and reusable views (Figure~\ref{fig:architecture}). The model receives the person, offering, cutoff, periods, task family, question, and shared feature/reference definitions. Structured requests let it run analytical batches, inspect compact results, and request more information or finish. Evaluation-only requirements remain hidden, and generated analysis code is not executed.

\subsection{Evidence and Answer Validation}
Evidence records connect each result to its feature, units, periods, counts, estimates, support, observation and assessment states, and uncertainty. They also retain source and configuration hashes, random seeds, and execution details. The model receives summaries rather than raw rows, while full evidence remains available for inspection.

Each peer comparison is identified by
\begin{equation}
I_{\mathrm{peer}}=(i,o,t,f,W_f,g,W_g),
\end{equation}
where $i$ is the person, $o$ the offering, $t$ the cutoff, $f$ the feature, $W_f$ the person's period, $g$ the reference group, and $W_g$ its period. A personal comparison instead uses
\begin{equation}
I_{\mathrm{personal}}=(i,o,t,f,W_b,W_r),
\end{equation}
where $W_b$ and $W_r$ are the earlier and recent periods. Readable identifiers are generated only for returned evidence, without using hidden expected answers.

Unknown, ambiguous, or altered identifiers are rejected without substitution or additional analysis. Repeated personal summaries are equivalent only when their person, feature, units, cutoff, periods, means, counts, change, and support match exactly. The system consistently selects one returned identifier and preserves the alternatives without creating a peer comparison.

Validation checks results against the trusted development data, including summaries, trajectories, counts, intervals, units, groups, periods, and eligibility. Changing values and recomputing their hash cannot bypass these checks. Displayed numbers must refer to validated fields, and unsupported scopes or identifiers fail even in correctly formatted responses. These checks establish consistency with the implementation, while scientific adequacy and answer completeness require separate assessment.

\subsection{Building and Tracing Answers}
The dashboard supports peer comparisons, personal change, assessment status, observation status, and measurement limitations. Selected comparisons become claims and panels, while personal results become claims and trajectories. Support rules determine whether the wording describes a result or explains insufficient observations. Unknown grades remain unavailable measurements.

The compiler adds required timelines, observation and assessment context, and qualifications without filling in missing comparison or personal claims. These additions can still answer a requested item, such as grade availability. Provenance therefore records model selections, identifier resolution, metadata, and compiler additions separately. All numerical calculation and insertion are deterministic. Model selection determines which content appears.

\subsection{Adaptive Presentation of Saved Answers}
The publication views were created after the experiment by reorganizing saved content. They introduce no evidence, changed periods, corrected omissions, or revised scores. Layout follows content rather than case identifiers. Equivalent personal duplicates may be combined with their original multiplicity recorded, while distinct peer claims remain available in expanded views. Evaluation uses the complete original dashboards.

Figure~\ref{fig:adaptation} shows how presentation changes with the available information. Personal views emphasize trajectories and selected peer comparisons. Observation views distinguish recorded zeros, ineligibility, and unavailable quantities, using timelines and grade context already supplied by the original compiler. Assessment views emphasize submissions per observed week and dated records. Every view includes expandable evidence and information about sources and methods.

\section{\uppercase{Experiment}}
\label{sec:experiment}
\noindent Four conditions answer identical questions about 24 additional development participants, with four cases per question family. Earlier development established the backend, agent policy, compiler, and evaluator. Its participants are excluded from the new cases, and its results are not pooled with this comparison.

\subsection{Cases and Shared Information}
The six question families address personal change alongside peers, comparisons between named reference groups, observation availability, separate limits on personal and recent peer comparisons, assessment submission and scheduled non-submission means with grade context, and alternative comparison periods. Reference questions do not automatically require personal change or a revised conclusion.

The fixed profiles compare weeks 0--3 with 8--11 at day~83, 0--3 with 4--7 at day~55, 0--1 with 2--3 at day~27, 0--3 with 10--11 at day~83, and 2--5 with 6--9 at day~69. Each question specifies its measure, periods, and cutoff. Selection uses administrative eligibility and previous attempt status where relevant. Cases testing insufficient observations require fewer than two recent eligible weeks and at least one earlier eligible week. Selection does not target model failures or extreme activity.

For each case, we select the unused eligible person with the smallest SHA256(seed, case, person), using seed \texttt{stage6-structural-v1-20260918}. All 57 previous and 24 new task participants are excluded from the shared peer pool across registrations. Cases use real observations. Separate calculations over source rows checked 52 fact records, providing an independent computational check rather than human review.

All conditions share questions, family labels, definitions, references, periods, and interpretation rules. Hidden facts support only scoring and later diagnosis. Tasks, prompts, code, schemas, sources, settings, scoring, and execution order were fixed before inference. There was no subsequent tuning or repetition of runs to obtain success.

\subsection{Conditions and Ablation}
\textbf{Enumeration} follows rules for the public question families and available references. It requests applicable reference comparisons and any required assessment measures. It uses the same backend, validator, renderer, and limit of six tool calls. Its access to family labels makes it a strong baseline for these defined tasks, without implying general language understanding.

\textbf{A, compact} selects answer types and returned identifiers, with the model specifying support and conclusion scope. The existing compiler constructs the dashboard.

\textbf{B, derived metadata} retains these selections but determines support and scope automatically, uses a neutral heading, and supplies a catalogue of returned answers. Comparing B with A therefore tests this combined interface change.

\textbf{C, explicit binding} selects exact analytical identifiers while retaining B's automatic metadata and identical catalogue. Comparing C with B tests how answers are identified while keeping available information equivalent. Comparing C with A tests the full intervention. None receives hidden scoring requirements or automatically supplied missing comparisons. An agent can still select a valid result that does not answer the question.










\subsection{Model, Budgets and Ordering}
Agents use Qwen2.5-14B-Instruct \cite{qwenReport,qwenCheckpoint}, revision \texttt{cf98f3b3bbb457ad9e2bb}\allowbreak\texttt{7baf9a0125b6b88caa8}. We use Transformers 4.55.2, the checkpoint's tokenizer and chat template, Torch 2.8.0+cu128, CUDA~12.8, BF16, and scaled dot-product attention. Parameters, inputs, and outputs remained on one RTX~6000 Ada GPU without quantization or CPU offload. CUDA profiling confirmed GPU execution.

Greedy decoding allows 16,000 input and 1,500 output tokens. Episodes permit six analytical calls, four generations, and one final repair using integrity errors and existing evidence, without completeness feedback. Failures and repairs remain recorded. Constrained decoding, training, and fallback answers are absent.

Enumeration used the host's CPU. Six A/B/C orderings repeat four times, balancing positions and pair order. One load served 72 agent episodes. All 96 combinations ran once. Timings are descriptive and sampling variability is untested.

\subsection{Outcomes and Their Interpretation}
An \emph{accepted output} passes format, support, scope, evidence, numerical, and rendering checks. First final validity excludes repairs but allows earlier tool errors. \emph{Complete visible answers} pass acceptance and every fixed requirement. Complete cases include required context. Optional panels earn no automatic credit.

\emph{Completeness through method selections} repeats checks without compiler-only claims, panels, or standard wording. Rules or agents select content. Tools calculate numbers. Insufficiency reports must match the feature, period, and comparison without excusing omissions.

Paired complete visible answers are primary. Selected completeness, validity, costs, and failures are secondary. Denominators retain all cases. Hidden requirements diagnose whether retrieved evidence could support complete answers. Significance is not tested. The prespecified target required 22/24 complete visible answers, no accepted unsupported quantities, and both answers in all four insufficiency cases.

\subsection{Evidence Retrieval and Failure Mechanisms}
The offline diagnostic found sufficient returned evidence for all 24 questions in both A and B, and 21 in C. In case~15, A nevertheless selected peer comparisons for weeks~0--3 when asked about weeks~10--11. Returned recent evidence supported a separate personal-insufficiency answer, but its peer answer was omitted (Figure~\ref{fig:failure}). Correct earlier wndow binding does not establish relevance.
C12 selected an earlier result for a requested recent mean. Invalid C18-20 analysis batches returned no evidence; final/repair handles remained unresolved. No catalogue had been returned, so its contents alone cannot explain those failures. A09 repaired peer selections paired with personal conclusion scope and A12 did not. A22 retained invalid scope, B23 repaired a panel limit error. These are trace observations, not established cognitive causes.
All 168 comparison generations reached end-of-sequence, with at most 491 output tokens, failures were not output limit truncation. Source checks detected no accepted unsupported quantitative answer among 91 accepted dashboards. This bounded result establishes agreement with checked fields/support rules, not universal semantic correctness or completeness.








\subsection{Unresolved Answer-Equivalence Caveat}
\label{sec:caveat}
B17-20 display both requested recent assessment means within supported personal change claims. The frozen focal item predicate recognizes a comparison panel or a supported comparison claim, but does not inspect a personal change claim for that mean. It therefore classifies eight requested items as retrieved but omitted even though their feature, units, recent window, and values appear on the page. This is an evaluation representation limitation, not a numerical failure. B remains 15/24 visible complete and 14/24 selected complete in every reported table and figure; no disputed case receives new credit.

C21/C23 display earlier and recent means in peer claims without an explicit personal-change answer; equivalence is a separate unresolved question. Unavailable forms and scoped insufficiency also require review. All 96 original slots, including rejections, are prepared for two reviewers and adjudication, but no ratings exist. Automated inspection is not independent human review, and frozen completeness is not a settled measurement construct.

\section{\uppercase{Discussion and Limitations}}
\label{sec:discussion}
\noindent The study demonstrates a practical architecture for combining agent selection, deterministic analysis, and adaptive dashboard views. Its central methodological contribution is making the path from a question to its displayed answer inspectable. This allows developers to distinguish calculation errors, unsuitable selections, missing answers, and context added automatically by the software. Case~15 illustrates the value of this separation. The agent identifies insufficient personal observations but selects earlier peer comparisons for a question about recent activity. Preserving that output exposes a specific selection problem that automatic completion would conceal.

\subsection{Lessons for Dashboard Design}
Compact A achieved the highest frozen agent completeness. B accepted more outputs, while C's explicit identifiers produced no gain in complete visible answers over B. These results show why successful construction and answer coverage should be assessed separately. B changes both metadata handling and catalogue availability, so its comparison with A evaluates that combined interface design. The traces identify concrete development priorities, including selecting the requested period, constructing valid requests, and covering every part of a question.

The attribution method also distinguishes model contributions from software assistance. Automatically supplied context can complete an answer without having been selected by the model. Conversely, B17--20 contain requested values in forms that the frozen evaluator does not credit. Recording both content and its origin supports a more informative assessment than counting panels or accepted outputs alone. Equivalent answer forms still require human adjudication.
Enumeration provides a reproducible operational baseline for the current registry and known task families. The shared backend makes its comparison with agents useful for assessing the cost and completeness of selection. Whether agents offer advantages for ambiguous questions, larger analysis libraries, or other domains remains a question for subsequent evaluation.

\subsection{Adaptive Views and Operator Context}
The interface examples show how the same analytical foundation supports different questions. In Figure~\ref{fig:reference}, the person's rate remains 3.50 clicks per eligible day while recent and earlier peer means are 3.46 and 6.98. The corresponding differences are +0.04 and $-3.48$, calculated before rounding. Displaying the periods and membership counts makes the reference choice inspectable without suggesting that one group is inherently preferable or that the difference is causal.

Assessment views preserve the timing needed to interpret apparently conflicting records. In A17, weeks~8--11 contain 0.25 non-banked submissions per observed week and zero scheduled non-submissions. A day-55 snapshot nevertheless records no submission for the day-54 assessment. These summaries describe different periods, and later submissions do not rewrite earlier snapshots. Grades and banking approval remain unavailable. The examples demonstrate implemented adaptation, while its effects on operator understanding and usability require direct evaluation.

\subsection{Scope and Further Validation}
The comparison covers 24 development people from two offerings. Its 96 outputs are paired method comparisons, not independent participants. Task families and wording were known, and one checkpoint with greedy decoding does not establish performance across models, paraphrases, or deployments. Reserved people remain unevaluated, and earlier development provides no independent confirmation.
The next validation step should resolve these judgments before fixing the system, evaluator, outcomes, and person-level sampling plan for reserved data. Any revised scoring should preserve the original results and be reported as a separate post hoc analysis. This progression builds on the implemented tool and its documented examples while keeping stronger reliability claims tied to independent evidence.

\section{\uppercase{Conclusion}}
\label{sec:conclusion}
\noindent The implemented dashboards connect agent selections with deterministic calculations, traceable evidence, and reusable presentation templates. Personal timelines, peer comparisons, observation summaries, and assessment views support different questions through shared analyses. Operators can inspect supporting records and switch among saved comparisons while retaining their analytical context.

Across 24 development cases, explicit analytical identifiers did not improve frozen completeness, while enumeration remained complete and cheaper. The evaluation nevertheless provides concrete guidance for system development. Correctly calculated values can refer to the wrong period or leave a question partly unanswered, while automatically supplied context can complete an answer without model selection. Tracking these contributions separately makes both successful behavior and remaining selection problems visible.

The contribution combines a working tool, interface examples, and reproducible evaluation of answer completeness. Answer equivalence and measurement choices require review before validation on reserved data. Evaluation should examine operator understanding and usability.
