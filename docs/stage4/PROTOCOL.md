# Stage 4 paired interface protocol v1

## Invariant science and data

Reuse the Stage 2 descriptive backend, source-bound row-loop numerical validator,
five feature definitions, three references, profile windows, support thresholds
(20 peers/two focal weeks), 500-replicate person bootstrap and primary repeated-row
treatment. See the immutable [Stage 3 analysis protocol](../stage3/ANALYSIS_PROTOCOL.md).
No mixed model supplies claims. Equal observed-week means within person, then
equal person weights, do not correct changing composition or unequal history.
Earlier-stage references are different descriptive questions, not fairer causal
controls. Intervals are peer-mean intervals, not individual prediction or contrast
uncertainty. Unknown logging, grade release and banking approval remain unknown.
No post-cutoff activity, final results or future withdrawal enters the model.

The verified development-only feature bundle is copied byte-for-byte; the shared
reference pool excludes all 33 historical focal people plus twelve new people
across registrations. Reserved trajectories are not opened. Fixed seed
`stage4-structural-v1-20260918` ranks eligible candidates by SHA256(seed, case ID,
person ID) in the existing twelve family/course/profile/eligibility slots. No
activity magnitudes or method outcomes determine selection. One explicit-measure
question per new person, two per family; six known Stage 3 cases for construction.
Task requirements and facts use the unchanged Stage 3 evaluator and independent
row-loop reducer. They are never agent/compiler inputs.

## Conditions and intervention

1. Existing strong enumeration baseline, unchanged selection logic.
2. Generic policy with the existing full Specification (evidence, claims, panels,
   conclusion); its investigation policy text is byte-identical to Stage 3.
3. The same generic policy with semantic intents and explicit conclusion scope.

Both agents have identical scientific instructions, public interpretation rules,
question, features/references, analysis tools, decoding and ceilings. Only final
schema/interface instructions and compilation differ. No coverage-aware phases,
request map, new investigation rules or tool deduplication. The bounded loop
retains Stage 3 scheduling and repair behavior. The optional Stage 3 task-state
fields are absent in both interfaces. Thus the control is the previous full
specification under this shared interface, not a byte-identical Stage 3 rerun.
Interface-specific strings are separate in `configs/stage4_prompts.json`.

Both use the exact unchanged source-bound integrity validator and panel contract:
at least one trajectory and observation panel; selected assessment evidence needs
assessment context; each selected evidence needs a claim and quantitative panel;
at most six evidence IDs, ten claims and ten panels. The compact compiler satisfies
these mechanical requirements and discloses additions. It cannot request tools,
read rubrics, route by task ID, select all retrieved evidence, or add a peer/change
claim that was not selected. Mapping is frozen in [INTERFACE.md](INTERFACE.md).

The Stage 3 controlled renderer is reused. Shared wrappers only label Stage 4,
show provenance and remove the inapplicable Stage 3 follow-up form from these
frozen exports. Chart/claim numerical bindings are unchanged. All conditions get
the same renderer and standard caveats. No scoring-specific content is inserted.

## Evaluation and mechanism

Use Stage 3 visible answer semantics without changing requirements or acceptable
answer forms. The primary endpoint is an accepted dashboard that answers every
requested item. First-final validity is distinct from final validity after one
repair. All twelve frozen cases stay in each condition's denominator.

Stage 3 assumed all spec panels/claims were method-selected. A necessary provenance
adapter now also scores a projection containing only explicitly selected content,
using the very same scoring predicates. Compiler-only context can contribute to
visible completeness but not method-selected completeness. Report each such item.
This attribution change is shared by baseline and full (their manually selected
content remains selected). It does not change Stage 3 primary scores or answer
semantics. No scoring feedback or oracle selection enters inference.

Mechanical observation/assessment panels may incidentally satisfy a contextual
request; this must be labeled compiler supplied unless explicitly selected as an
intent. They cannot add an omitted window-mean peer comparison or personal change.
The compiler's per-evidence fallback claim is only the same public measurement
boilerplate already shown by every renderer. Optional extra panels earn no bonus.

Preserve observable raw actions, tool results, semantic selections, compilation
provenance, errors, repairs, accepted specs and outputs. Separate missing evidence,
retrieved-but-omitted answers, structural errors, unsupported selections/conclusions,
scoped insufficiency, shared context, repeated calls, tokens and latency. Report
paired compact-versus-full gains, losses and unchanged cases. Valid JSON/rendering
alone is not success. No significance or general-superiority claim is planned.

Stage 3 diagnosis is explicitly oracle-assisted: independent source validation of
retrieved evidence, evaluator-based answer availability, and selected-answer
projections ignoring rejected layout. These are diagnostic upper bounds/intents,
not deployable methods, counterfactual agent successes or pilot input. Multiple
failure labels may apply. Raw parse position, schema errors and actual token ceiling
are inspected; absent EOS evidence in Stage 3 cannot prove truncation. Stage 4
records ending token/EOS and token ceiling directly.

## Freeze, execution and stopping

Freeze questions, selection rules, hidden requirements/facts, public prompts and
schemas, compiler mapping, configs, code, source hashes and execution order before
any pilot method. Run baseline on GPU-host CPU, then both agents on all twelve
cases. Full first for odd cases, compact first for even: six first positions each
and one each within every family. One shared pilot model load. Same pinned revision
`a09a35458c702b33eeacc393d103063234e8bc28`, Transformers 4.55.2, BF16 CUDA, greedy
decoding, 1,500 output tokens and 16,000 input tokens. Setup/profiling is counted
separately within eight calls. Runtime includes initialization and cleanup; shared
loading/profile overhead is not assigned to one method. Order balances but does
not remove cache or temporal effects. This is one run, not repeatability evidence.

No pilot reruns, baseline substitution or tuning after results. Readiness target:
11/12 compact complete valid visible answers with zero accepted unsupported
quantitative answers; report stricter selected-answer endpoint alongside it.
Inspect the first selected case in all six families for all three conditions;
keep failed cases in that selection. Replay every accepted saved result without
inference; verify source, exclusions, frozen/history hashes, budgets and CUDA proof.
Only focused interface, attribution, scoring-compatibility and loop checks are
required. Scientific/human review remains outstanding. Negative results end the
stage rather than triggering another policy or larger model.
